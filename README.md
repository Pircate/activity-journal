# 我的运动记录

使用 Intervals.icu 真实记录的中文运动日志：[访问网站](https://pircate.github.io/movement-journal/)。

## 页面内容

展示截至北京时间当天最近 365 天的累计距离、运动时长、运动次数、最近一周的运动记录和全年活动热力图。可切换距离、时长和 Intervals.icu 训练负荷，也可用日期选择器或方向键查看每天的指标。

全年活动下方的运动装备库按自行车展示在用配件和累计里程，不受最近 365 天范围限制。链条、前胎、后胎按 5000 km，飞轮按 10000 km，牙盘按 30000 km 显示更换进度；达到 80% 提示“即将到期”，达到目标提示“建议更换”，超期保留实际里程。

## 装备维护

在 Intervals.icu 的装备中维护自行车及配件，网站只读取信息，不提供编辑或重置操作：

- 将配件关联到自行车，也支持轮组下的外胎；已退役装备隐藏，共享配件在各所属自行车下展示。
- 链条使用 `Chain`、飞轮使用 `Cassette`、外胎使用 `Tyre`、牙盘使用 `Chainrings` 类型。前后外胎分别建配件，名称以“前胎”“后胎”开头，例如“前胎 GP5000”；未标位置的外胎照常显示，但明确提示位置未标记。
- 为每个链条、飞轮、外胎和牙盘设置唯一一个名为“更换”的提醒。每次换件后重置该提醒；重置时间按北京时间显示为最近更换日期，重置后的使用里程来自 `distance_used`。补胎液、上蜡等其他提醒不参与更换统计。
- 网站目标固定为链条及外胎 5000 km、飞轮 10000 km、牙盘 30000 km；建议平台提醒也设置相同里程，网站不修改平台设置。
- 缺少提醒、提醒重名、未提供重置日期或更换后里程时明确展示缺失；不使用购买日期或配件累计里程推断。自行车和普通配件使用平台累计里程。

历史换件需要单独补录：Intervals.icu 新建或更新提醒会忽略传入的历史 `last_reset`，仅修改购买日期也不会重算提醒。补录时创建零里程配件，将已知实际装车日期写入 `purchased`，先创建从零开始的“更换”提醒，再关联自行车。活动完整时可读取该配件 `/calc` 的统计并保存；已有用户确认的里程基准时应保留该基准，避免用不完整活动重算覆盖。实际更换日期以“运动装备库更换记录：”开头的 JSON 行保存在该配件备注中，字段为 `date`（日期未知时为 `null`）、`reminderId`、`resetAt`、`baseline`（提醒的起始距离、时间、次数数组）。网站只在提醒标识、重置时刻和起始计数均与补录时一致时使用这个明确记录的日期；未知日期显示“未记录”，之后重置提醒自动使用新的重置日期。备注内容及其中的内部标识不会发布。

青野与 R200 共用同一个链条和牙盘配件，分别关联到两个装备条目，平台负责累计两边的新骑行里程。外胎仅关联青野。网站直接读取配件计数，不将两处展示的共享配件重复相加。

尚未完成首次装备同步时显示“装备尚未同步”；成功查询但没有在用自行车时才显示空列表。首次有授权的成功同步会填充装备库。

## 自动更新

每天北京时间 22:00 的「每日同步 Strava/Garmin/COROS 运动数据」任务完成三端同步后，按 [网站更新说明](docs/SITE-SYNC.md) 从 Intervals.icu 获取最近 365 天完整记录、更新本仓库并触发 GitHub Pages 发布。同步存在阻塞或失败、Intervals.icu 查询失败或返回无效记录时保留上一版数据。任务在本机 Codex 中执行，需要本机与 Codex 可运行、网络畅通且 Intervals.icu 与 GitHub 授权有效。

页面打开、从后台返回时都会绕过浏览器缓存读取 `docs/activities.json`，页面保持打开时每 5 分钟再检查一次。热力图每日自动滚动，尚未同步的日期不算作已确认没有运动的日期。

每条公开活动记录仅含北京时间日期、中文运动类型、距离、运动时长和训练负荷。装备仅公开名称、类型、里程和更换摘要。缺失距离或负荷保留为 `null`；不发布坐标、心率、账号信息、原始活动或装备标识、装备备注或凭据。

## 同步脚本

使用 Node.js 22 或更新版本。先在仓库外配置环境变量：

- `INTERVALS_ICU_API_KEY`：从 [Intervals.icu 设置](https://intervals.icu/settings) 底部 Developer Settings 获取的个人 API Key。
- 或 `INTERVALS_ICU_TOKEN`：具有活动及装备读取权限的现有 OAuth Token；同时配置时优先使用此项。

不要将凭据写入代码、公开 JSON 或 Git。脚本先解析当前账号，再查询最近 365 天的完整活动及装备列表，全部校验成功后原子替换同一份公开快照。活动或装备任一请求失败时均保留上一版。重复运行不会累积重复记录，也不会混入此前 COROS 来源的数据。

```sh
node scripts/update-data.mjs
node scripts/build.mjs
node --test scripts/*.test.mjs
```

字段来自 [官方 API 文档](https://intervals.icu/api-docs.html)：`distance` 从米转为公里，`moving_time` 为运动秒数，`icu_training_load` 为活动训练负荷。使用 UTC 开始时间 `start_date` 转换北京时间日期；API 查询范围两端各扩大一天，以覆盖跨时区活动。保留同一天的多次运动，不按日期去重。

API 不提供部分 Strava 来源活动的完整内容；这些记录仅在 `unavailableActivities` 中保留平台提供的当地日期，页面明确标注缺失，不计入距离、时长和次数。其他缺失运动时长、重复活动 ID、无效记录或达到查询上限的情况会让整次同步失败并保留旧文件。不使用旧来源的数据补齐；可读取活动缺失的距离和负荷保留为空。

`activities.json` 顶层包含 `period`、`syncedAt`、`activities`、`unavailableActivities` 和 `gearLibrary`。`gearLibrary` 首次未同步为 `null`，成功同步后为自行车数组；每辆车仅含 `name`、`type`、`distanceKm`、`components`。配件仅含 `name`、`type`、`distanceKm`、`replacement`。普通配件的 `replacement` 为 `null`；重点配件的更换摘要包含 `status`（`available`、`missing-reminder` 或 `duplicate-reminder`）、`date`、`distanceKm`，其中未知日期和里程为 `null`。不接受缺少装备字段的旧数据结构。

同步与构建成功后，将更新文件提交并推送到 `main`，GitHub Pages 从 `docs/` 自动发布。网页只读取同源公开 JSON，凭据仅在本机脚本运行时使用。
